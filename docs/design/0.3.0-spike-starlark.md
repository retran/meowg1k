# M0 spike: starlark-rust

Status: done. Run against `starlark` 0.14.2 on 2026-09-19. The spike code was
thrown away; this is what it found.

## The question

`docs/design/0.3.0-architecture.md` section 3 builds the whole execution model
on one claim about `starlark-rust`, and section 12 puts this spike first
because a bad answer would invalidate `starlark.md` and `agent.md`. The
question: how much does the value model fight a design that wants modules to
reach an async engine?

## The answer

The design holds. Nothing in `starlark.md` or `agent.md` needs an amendment.
One sentence of the architecture document was wrong about why, and that is
corrected in this change.

## What was checked

### A builtin can block on the async engine

A builtin reached a `tokio::runtime::Handle` through `Evaluator::extra`,
called `block_on`, and returned the result to the script. The evaluator ran
inside `tokio::task::spawn_blocking`, which is not an async context, so
`block_on` does not panic there.

```text
== Q1: builtin blocks on async from a spawn_blocking thread ==
Ok("\"ENGINE ANSWERED AFTER 40MS\"")
```

`Evaluator::extra` is an `Option<&dyn ProvidesStaticType>` and accepted a
stack-local struct, so the engine handle does not need to be `'static`. That
is the mechanism [R-STAR-010] asks for: one context object, reached the same
way from every module.

### Two evaluators run concurrently

Two scripts ran on two blocking threads at once, each with its own evaluator,
each blocking on the engine. Both returned.

```text
== Q2: two evaluators on two blocking threads at once ==
Ok("\"engine answered after 60ms\"")
Ok("\"engine answered after 20ms\"")
```

This is what `meow.parallel` needs, and it confirms that the restriction in
[R-STAR-044] is about values rather than about concurrency.

### A custom loader implements all three schemes

A `FileLoader` intercepted `@std//`, `@pkg//`, and `//` and returned a
distinct error for each, which is what [R-STAR-003] to [R-STAR-005] require.

### Diagnostics already carry spans

This was the pleasant surprise. `starlark-rust` renders its own diagnostic
with a call stack and a source span:

```text
Traceback (most recent call last):
  * spike.star:4, in <module>
      go()
  * spike.star:2, in go
      return read("missing.txt")
error: fs.read: missing.txt: no such file
 --> spike.star:2:12
  |
2 |     return read("missing.txt")
  |            ^^^^^^^^^^^^^^^^^^^
```

[R-STAR-090] wanted the file, line, and column on every error, and the
architecture document proposed rendering them through `miette`. That is
unnecessary for Starlark errors: the library already does it, and better,
because it carries the call stack too. `miette` still earns its place for
configuration and command-line errors, which have no Starlark frame.

## The correction

The architecture document said:

> `starlark-rust` evaluators are `!Send`. A Starlark value cannot cross a
> thread boundary.

The first sentence is right and the second is wrong. `Value` implements both
`Send` and `Sync`. What stops a value crossing a thread is its lifetime: a
value borrows the heap it lives in, `Module` is not `Send`, and a heap cannot
outlive the closure `Module::with_temp_heap` scopes it to. Moving a value into
`std::thread::spawn` and reading it there fails to compile, with

```text
error[E0521]: borrowed data escapes outside of closure
```

The conclusion is unchanged - one evaluator per thread, and concurrency
expressed over declarations rather than closures - but the reason matters,
because someone reading "values are not Send" would look for a `Send` bound
that is not there and conclude the constraint had been lifted.

## What it changed

`Module::with_temp_heap(|module| ...)` scopes the module to a closure in
0.14, rather than handing back a value. The evaluator therefore lives inside
that closure, on the blocking thread, which is exactly the shape section 3.2
already describes. Nothing to change, but implementers should expect the
closure rather than a constructor.

`Module::with_temp_heap_async` also exists. It does not help: builtins are
synchronous functions, so blocking inside one from an async context would
panic. The blocking thread stays.

## What was not checked

- **Cancellation.** Whether a `block_on` inside a builtin can be interrupted
  from outside, which [R-AGENT-030] needs. The likely shape is that the
  blocking call selects on the cancellation token and returns an error the
  builtin propagates, unwinding the script. M4 has to prove it.
- **Memory under a long run.** Every value lives in the arena until the
  closure ends, so a forty-step run holds everything. Whether that matters is
  a measurement for M4, not a design question.
- **Frozen modules across `load`.** The spike returned errors from the loader
  rather than real `FrozenModule` values, so the freeze path is unproven. M7
  covers it.
