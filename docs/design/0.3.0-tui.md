# meowg1k 0.3.0 — Terminal UI

Status: design, not yet implemented. Third of three documents; see
`0.3.0-architecture.md` for the runtime and `0.3.0-starlark-api.md` for the
scripting surface.

## 1. What the UI is for

meowg1k is a command in a shell pipeline, not an application you sit inside. The
terminal layer has exactly two jobs:

1. **Make a running agent auditable.** The user must be able to see, live, what
   the agent is doing, what it is about to do, what it has spent, and stop it.
2. **Leave behind output that is still useful after the process exits** — in
   scrollback, in a pipe, in a CI log, in a JSON parser.

Those two jobs pull in opposite directions, and almost every defect in the 0.2.x
terminal layer comes from not having decided between them.

## 2. What 0.2.x got wrong

| Defect | Evidence | Consequence |
| --- | --- | --- |
| Three rendering stacks, concurrently live | `internal/adapters/progress/tty_logger.go` (uilive), `internal/adapters/output/tui/program.go` (Bubble Tea, 807 lines), `internal/ui/*.go` (lipgloss) | Each owns the cursor; which one wins is timing-dependent |
| The script does layout | `ctx.ui` exposes 22 builtins — `panel`, `table`, `tree`, `pager`, `divider`, `banner`, `progress_bar` | Presentation is decided in userland, so it is inconsistent across commands and unfixable centrally |
| Diagnostics bypass the renderer | 10 `log.Printf` sites in `module_llm.go`, `fmt.Print` in `module_ui.go` and `internal/ui/input.go` | Writes straight through the live frame and corrupts it |
| The script drives the step model by hand | `turn = ctx.ui.assistant_turn()`, `step = turn.step("Preparing")`, `step.done()` | Every command reimplements the same ceremony; `lib/ui_helpers.star` exists to hide it |
| No machine-readable mode | — | The tool cannot be composed with anything; `meow review \| jq` is impossible |
| No approval surface | Policy does not exist in 0.2.x | There is nowhere to put the one interaction that matters most |

The rewrite collapses three stacks into one and moves the layout decision out of
Starlark entirely.

## 3. Model: one event stream, three renderers

The engine emits a single typed stream (`EventSink` in `meow-agent`). Renderers
consume it. **The script never chooses a renderer and never draws**; the runtime
selects one from the environment.

```text
            AgentEngine
                 │  AgentEvent
                 ▼
     ┌───────────┴───────────┐
     │           │           │
  TtyRenderer  PlainRenderer  JsonRenderer
  isatty       piped / CI     --format json
```

| Renderer | Selected when | Output |
| --- | --- | --- |
| `tty` | stdout is a TTY and `--format` is unset | Inline live rendering, colour, spinners |
| `plain` | stdout is not a TTY, or `NO_COLOR`, or `--color=never` | Line-oriented, no ANSI, no cursor movement, stable under `tee` |
| `json` | `--format json` | JSONL — one typed event per line, schema-versioned |

`json` is what makes this a CLI automation tool rather than a demo. Every event
the TUI can draw is an event a script can parse:

```console
$ meow review --format json | jq -c 'select(.type=="finding")'
{"type":"finding","severity":"high","file":"src/retry.rs","line":61,"summary":"…"}
{"type":"finding","severity":"low","file":"src/cli.rs","line":12,"summary":"…"}

$ meow review --format json | jq -s 'map(select(.type=="usage")) | last'
{"type":"usage","prompt":71204,"completion":3188,"total":74392,"cost_usd":0.214}
```

The three renderers share no code beyond the event type, and each is tested by
feeding it a recorded event log — which also means the TTY renderer is testable
without a terminal.

## 4. Layout: transcript-first, not dashboard

The single most consequential decision: **meowg1k does not take over the
screen.**

A full-screen alternate-buffer TUI is wrong for this tool. When it exits, the
screen is restored and the entire run is gone — no scrollback, nothing to paste
into an issue, nothing for `tee` to have captured. Every agent run is something
the user will want to read again.

So: the transcript is printed into normal scrollback, permanently, line by line
as it is finalized. Only a small **live region** at the bottom is redrawn.

```text
▌ review · smart · session 4f2a9c                                   ← header, printed once
│
├─ 1  fs.read          src/retry.rs                          12ms   ← finalized: never redrawn
├─ 2  git.diff         HEAD                                  31ms
├─ 3  search.code      "retry budget"                       0.42s
│     ↳ 4 matches in 3 files
├─ 4  shell            cargo test --lib                       8.1s
│     ⚠ allowed by rule  shell: "cargo *"
│
│  The retry loop in `RetryWithBackoff` treats every error as retryable.
│  An authentication failure therefore costs the full backoff schedule
│  before it surfaces…
│
├──────────────────────────────────────────────────────────────────
│ ⠹  search.code "auth error classification"              0:04       ← live region
│    step 5/40   ▊▊▊▊▊▁▁▁▁▁  74k/200k tok   $0.19
└──────────────────────────────────────────────────────────────────
```

On completion the live region is replaced by a one-line footer and also becomes
permanent:

```text
└─ finished · 12 steps · 74.4k tok · $0.21 · 1m04s · session 4f2a9c
```

### 4.1 Mechanism

`ratatui` with `Viewport::Inline(n)` rather than `Viewport::Fullscreen`. The
inline viewport owns only the bottom `n` rows; `Terminal::insert_before` emits
finalized lines into scrollback above it. This is precisely the shape described
above and is why `ratatui` is the right choice over a hand-rolled ANSI layer.

Three properties fall out, and all three are things 0.2.x cannot do:

- **Killing the process leaves valid output.** Everything above the live region
  was already committed to scrollback. `Ctrl-C` cancels the run, the live region
  is replaced by `cancelled · 5 steps · …`, and the transcript survives.
- **Resize is not a redraw of history.** Only the live region reflows.
- **`tracing` output has somewhere to go.** The log writer uses
  `insert_before`, so a warning appears in the transcript in order instead of
  tearing through the frame. `println!` is denied by lint outside `meow-cli`.

### 4.2 Non-TTY is the same transcript

The `plain` renderer emits the same structure without box drawing, colour, or
the live region:

```text
review: model=smart session=4f2a9c
  1 fs.read src/retry.rs (12ms)
  2 git.diff HEAD (31ms)
  3 search.code "retry budget" (0.42s) -> 4 matches in 3 files
  4 shell cargo test --lib (8.1s) [allowed: shell "cargo *"]
finished: 12 steps, 74392 tokens, $0.21, 1m04s
```

This is what lands in a CI log, and it is deliberately greppable.

## 5. The script's surface

`ctx.out` is **semantic, not presentational**. The script says what a thing
*is*; the renderer decides how it looks in each of the three modes.

```python
ctx.out.write(text)                      # a line of plain output
ctx.out.markdown(text)                   # rendered in tty, raw in plain, string in json
ctx.out.note("nothing to review")        # de-emphasised aside
ctx.out.warn("stopped on budget")        # warning
ctx.out.error("could not resolve HEAD")
ctx.out.step("collecting diffs")         # a labelled phase in the transcript
ctx.out.table(rows, columns = [...])
ctx.out.diff(patch)
ctx.out.finding(severity, location, summary)
ctx.out.json(value)                      # structured payload, first-class in --format json
```

Eleven semantic calls replace 0.2.x's 22 layout builtins. Everything that was
presentational is gone:

| Removed | Why |
| --- | --- |
| `panel`, `divider`, `banner`, `tree` | Decoration decided in userland; the renderer owns framing now |
| `progress_bar`, `progress` | The live region shows progress automatically; a script driving its own bar fights the renderer |
| `pager` | That is `less`'s job, and a pager is actively wrong in a pipe |
| `code`, `render` | Folded into `markdown` |
| `assistant_turn` / `turn.step()` / `step.done()` | The engine emits step events; the script no longer narrates them |
| `user_turn` | Ditto |

Interaction stays, because agents genuinely need it, but narrows to three:

```python
ctx.ask.text("Commit message?", default = suggested)
ctx.ask.confirm("Push to origin/main?", default = False)
ctx.ask.select("Which branch?", options = branches)
```

All three fail loudly rather than blocking when stdin is not a terminal or
`--yes` is set — an unattended run must never hang on a prompt.

## 6. Approval: the interaction that matters

Policy `ask` (see the API document, §9) is the one place the tool must interrupt
the user, and it gets a dedicated surface. The prompt takes over the live region
only; the transcript above it is untouched.

```text
├─ 7  shell            git push origin main
│
│  ┌─ approval required ───────────────────────────────────────┐
│  │  shell.run                                                │
│  │    git push origin main                                   │
│  │                                                           │
│  │  matched  ask  shell: "git push *"                        │
│  │  agent    release · step 7/40                             │
│  │                                                           │
│  │  [y] once   [a] always this session   [n] deny   [s] stop │
│  └───────────────────────────────────────────────────────────┘
```

Four properties, each a deliberate choice:

- **The exact command is shown verbatim**, never a summary. An approval prompt
  that paraphrases what it is approving is worse than no prompt.
- **The matching rule is named**, so the user learns why they are being asked
  and can narrow the policy afterwards.
- **`always` is session-scoped**, never written back to `meow.star`. Persisting
  a grant from inside a prompt is how permission systems rot.
- **Non-interactive means deny.** With `--yes` or no TTY, `ask` resolves to
  `deny` and the decision is recorded. Degrading to `allow` would make the
  policy decorative.

Every outcome, including a timeout, is appended to the session log as a
`PolicyDecision` event, so `meow session show` reconstructs exactly what the
agent was permitted to do.

## 7. Interactive mode

`meow chat` is the one place a full-screen view is right, because there the
terminal *is* the application rather than a pipeline stage. It gets
`Viewport::Fullscreen`, a scrollback pane, an input line, and `Ctrl-C` to
interrupt the current turn without exiting.

It is explicitly secondary. It shares the event stream and the widget set with
the inline renderer and adds nothing to the engine. If it slips a release,
nothing else is blocked.

## 8. Theme and accessibility

```python
# .meow/meow.star
meow.theme(
    accent   = "#c792ea",
    success  = "#a3be8c",
    warn     = "#ebcb8b",
    error    = "#bf616a",
    muted    = "#5c6370",
    unicode  = True,       # box drawing and spinners; False falls back to ASCII
)
```

- `NO_COLOR` is honoured unconditionally, as is `--color=never`.
- Colour depth is detected (truecolor / 256 / 16 / none) and the palette is
  quantised rather than dropped.
- `unicode = False`, or a terminal that cannot be shown to support it, falls
  back to ASCII box drawing and a textual spinner.
- Colour is never the only carrier of meaning: severity and status always carry
  a word or a sigil as well, which is also what makes the `plain` renderer a
  faithful downgrade rather than a lossy one.

## 9. Crate shape

```text
meow-ui/
  event.rs       the AgentEvent -> view-model mapping, shared by all renderers
  tty/           ratatui inline viewport, live region, transcript committer
  plain/         line-oriented writer
  json/          JSONL writer, versioned event schema
  ask/           approval and input prompts
  theme.rs       palette, colour-depth quantisation, unicode fallback
  widgets/       step line, tool line, budget meter, diff, table, findings
```

`meow-ui` depends on `meow-core` for the event types and on nothing else in the
workspace. It does not know the engine exists, which is what lets the renderers
be tested against a recorded log and lets the engine be tested with no renderer
at all.
