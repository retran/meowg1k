# meowg1k 0.3.0 - Implementation plan

Status: draft. Sequences the 262 requirements in `docs/spec/` into ten
milestones. Replaces the rough ordering in `0.3.0-architecture.md` section 12,
which predates the specifications.

## How to read this

Every milestone names the requirements it closes, what it depends on, and the
thing you can do at the end of it that you could not do before. That last part
is the test of whether a milestone is cut in the right place: a milestone whose
result cannot be demonstrated from a shell is a milestone that was cut by
layer instead of by behaviour.

Each milestone decomposes into issues with `/plan`. The issue list is not in
this document, because it goes stale the moment work starts and GitHub is
better at tracking it.

Every one of the 262 requirements appears in exactly one milestone. The
coverage table at the end is generated from the specifications and the
assignment below, so a requirement cannot be quietly dropped.

## M0: Spike

**Goal.** Find out how much the `starlark-rust` value model fights the module
design before anything is built on the answer.

**Requirements.** None. A spike closes no requirement; it settles a design
question.

**What to build.** Three real `@std//` modules, one builtin that blocks on an
async call through a `tokio::runtime::Handle`, and one script that calls all
four. Throw it away afterwards.

**What it answers.** Whether a module can hold the runtime handle it needs
given that `Evaluator` and every Starlark value are `!Send`; whether a custom
`FileLoader` can implement the `@std//`, `//`, and `@pkg//` schemes;
and what a Starlark error looks like when it has to carry a source span out to
`miette`.

**Why first.** If the answer is bad it changes `starlark.md` and `agent.md`,
and both are cited by later milestones. Every week this is delayed is a week
of work that might be built on a wrong assumption.

## M1: Foundations, workspace and store

**Goal.** One SQLite database per workspace that opens, migrates, and stores
content-addressed blobs.

**Requirements.** All 25 `R-STORE-*`.

**Depends on.** Nothing.

**What you can do at the end.** `meow init` creates `.meow/`, and a test
binary writes a blob, reads it back by hash, and survives a reopen at a newer
schema version.

**Notes.** [R-STORE-021] is the requirement to hold the line on. It is one line
of code and the whole reason the v0.2.x session log cannot be trusted. Write
the test that proves a failed write propagates before writing the write path.

## M2: The session log

**Goal.** An append-only log that records a run and replays it two ways.

**Requirements.** `R-SESSION-001` to `006`, `010` to `013`, `020` to `022`,
`030` to `033`, `040` to `043`, `060` to `061`, `070` to `071`. 25 in total.

**Depends on.** M1.

**What you can do at the end.** `meow session list` and `meow session show`
work against a log written by a test fixture, and a compacted range still
renders in full.

**Notes.** [R-SESSION-011] and [R-SESSION-012] are the two rebuild modes, and
they are the pair most likely to be implemented as one function with a flag and
then to drift. Write them as two functions over one iterator.

## M3: Model transport

**Goal.** One provider behind a trait that no vendor type crosses.

**Requirements.** All 29 `R-LLM-*`.

**Depends on.** Nothing, though it is cheaper after M1 because the response
cache already exists.

**What you can do at the end.** A test binary streams tokens from Anthropic to
stdout, and an invalid API key fails in under a second instead of after the
full backoff schedule.

**Notes.** Build the error classification ([R-LLM-030] to [R-LLM-033]) before
the happy path, because retry behaviour is what the v0.2.x gateway got wrong
and it is hard to retrofit. Anthropic first: it exercises tool calling,
streaming, structured output, and prompt caching, so a second provider is
filling in a shape rather than discovering it.

## M4: The agent engine

**Goal.** The loop, with an outcome that explains itself.

**Requirements.** `R-AGENT-001` to `005`, `010` to `017`, `020` to `025`,
`030` to `032`, `070` to `073`, `080` to `081`. 28 in total.

**Depends on.** M2 for the session writes, M3 for the model calls.

**What you can do at the end.** `meow run` takes a task and a hard-coded tool,
runs the loop, and prints an outcome with a stop reason, a token count, and a
cost. Ctrl-C stops it and leaves a readable transcript.

**Notes.** This is the vertical slice that proves the threading model end to
end: a blocking script thread, an async engine, and a cancellation token
crossing between them. [R-AGENT-021] and [R-AGENT-022] look small and are the
correctness core of the whole tool.

## M5: The permission boundary

**Goal.** No tool runs without a decision, and every decision is recorded.

**Requirements.** All 29 `R-POLICY-*`, plus `R-AGENT-006`.

**Depends on.** M4 for the call site, M2 for the audit events.

**What you can do at the end.** An agent with `shell.run` cannot run anything
the policy does not allow, `meow policy explain` predicts the decision without
triggering it, and `meow session show --tools` lists the denials.

**Notes.** This is the milestone that makes the tool safe to point at a
repository, so it comes before the Starlark surface rather than after.
[R-POLICY-011], deny by default, is the requirement that makes the rest mean
anything; write its test first.

## M6: Compaction, sub-agents, and concurrency

**Goal.** Long runs, nested runs, and parallel runs.

**Requirements.** `R-AGENT-040` to `043`, `050` to `053`, `060` to `062`.
13 in total.

**Depends on.** M4, M5, and M2's compaction events.

**What you can do at the end.** An agent runs past its context window without
failing, calls another agent as a tool, and fans one agent out over three
inputs concurrently.

**Notes.** Concurrency here is Rust-side only. The constraint from M0 decides
how `meow.parallel` is shaped in M7, which is why this milestone precedes it.

## M7: The Starlark surface

**Goal.** Users write agents.

**Requirements.** All 38 `R-STAR-*`.

**Depends on.** M4, M5, M6. The engine must be complete, because `meow-star`
declares to it and never the other way round.

**What you can do at the end.** A `.meow/` directory with a Starlark agent, a
markdown agent, and a custom tool works, and `meow <agent>` runs from the
shell.

**Notes.** [R-STAR-010] and [R-STAR-011] are the fix for the defect that cost
v0.2.x the most: two context builders that drifted. Build the module table
first and let everything else consume it, rather than building modules and
collecting them later.

Split into three changes, because the declaration phase and the run phase have
no code in common and reviewing them together would double the size of one
pull request for no gain:

1. Discovery, the load scheme, the declaration phase, arguments, schemas, and
   diagnostics: [R-STAR-001] to [R-STAR-007], [R-STAR-010], [R-STAR-031] to
   [R-STAR-033], [R-STAR-060] to [R-STAR-063], [R-STAR-070], [R-STAR-071],
   [R-STAR-080], [R-STAR-082] to [R-STAR-084], [R-STAR-090], and
   [R-STAR-091]. Twenty-three requirements.
2. The full agent declaration and markdown agents: [R-STAR-040] and
   [R-STAR-050] to [R-STAR-054]. Six requirements. These need nothing from the
   run phase, because declaring an agent and running one are separate.
3. The handler context, agents as values, and the blocking bridge:
   [R-STAR-011], [R-STAR-020], [R-STAR-021], [R-STAR-030], [R-STAR-041] to
   [R-STAR-044], and [R-STAR-081]. Nine requirements.

[R-STAR-030] belongs to the third change even though the check it asks for
lands with the first: refusing a declaration outside the declaration phase can
only be tested once there is a handler to call it from.

The `@std//` table starts with the modules that reach nothing outside the
process: `env`, `json`, `path`, and `text`. The rest of the table
`0.3.0-starlark-api.md` section 10 lists - `fs`, `shell`, `git`, `http`,
`search`, `index`, `store`, and the remaining encoders - waits for the policy
gate, because a capability module has to be checked before it acts and putting
that check inside the module would make permissions a decision two places get
to make. `search` and `index` land in M10 with retrieval; the others land in
M11 with the port, which is also when the shipped agents need them.

## M8: The terminal

**Goal.** Three renderers over one event stream, and exit codes a shell can
branch on.

**Requirements.** All 38 `R-TUI-*`.

**Depends on.** M4 for the events, M5 for the approval prompt, M7 for
`ctx.out`.

**What you can do at the end.** `meow review` renders live, `meow review |
cat` renders plainly, `meow review --format json | jq` parses, and
`meow review --strict && git push` gates on the result.

**Notes.** Write the plain and JSON renderers first. They need no terminal, so
they are testable from a recorded log, and building them first stops
terminal-only assumptions from leaking into the shared event handling.

Split into two changes, because the renderers and the command line share no
code and each is large enough to review on its own:

1. `meow-ui`: the event vocabulary, the three renderers, renderer selection,
   the theme, and `ctx.out`'s ten calls. [R-TUI-001] to [R-TUI-005],
   [R-TUI-010] to [R-TUI-016], [R-TUI-020], [R-TUI-021], [R-TUI-030] to
   [R-TUI-034], [R-TUI-040] to [R-TUI-042], and [R-TUI-090] to [R-TUI-093].
   Twenty-six requirements.
2. `meow-cli`: the command surface and the exit codes. [R-TUI-070],
   [R-TUI-071], [R-TUI-080], and [R-TUI-081]. Four requirements.
3. Interaction and the run flags: [R-TUI-050], [R-TUI-051], [R-TUI-060] to
   [R-TUI-062], [R-TUI-072], and [R-TUI-073]. Seven requirements.

[R-TUI-074], `--continue`, moves to M9. Resuming means seeding the engine with
the session's own messages, which is the session log's job and not the command
line's.

[R-TUI-016] and [R-TUI-060] were amended on 2026-09-20: `ratatui` fixes an
inline viewport's height when the terminal is constructed and offers no way to
take the backend back, so the live region cannot grow for a prompt. The prompt
is committed to the transcript instead, which costs no reflow and leaves the
question and its answer where somebody can find them.

The binary builds one engine per declared provider and picks between them by
the provider a model names. The engine takes one provider and has no way to
know which vendor serves `claude-haiku-4-5`; the declarations do, and they live
in `meow-star`, so the choice is made there.

`trust`, `auth`, and `index` have no subcommands yet. A group with nothing in
it is worse than no group: it tells a reader something exists. `auth` arrives
with credential storage in M11, `index` with retrieval in M10, and the
`session` group with M9.

The live stream and the session export share one type rather than one
convention: `ViewEvent::Logged` carries an `EventKind` unchanged and serde's
untagged representation makes [R-TUI-032] hold by construction. A parallel
vocabulary for the live stream would have to be kept level by hand, which is
the shape of every schema that drifts.

## M9: Continue, branch, retain, export

**Goal.** A run you can return to.

**Requirements.** `R-SESSION-050` to `054`, `080` to `082`, `090` to `093`.
12 in total.

**Depends on.** M2, M4, M8 for the export renderers.

**What you can do at the end.** `meow review --continue` adds a follow-up,
`meow session fork <id> --at 8 --model fast` reruns from step eight, and
`meow session export <id> --format md` produces something you can attach to a
pull request.

**Notes.** Fork is the operation that makes agents debuggable, and it is
cheap once the log is append-only and blobs are refcounted. It is this late
only because it has nothing to prove until there are real runs to fork.

Split into two changes:

1. Fork, retention, and export in `meow-session`: [R-SESSION-052],
   [R-SESSION-053], [R-SESSION-080] to [R-SESSION-082], and [R-SESSION-090] to
   [R-SESSION-093]. Nine requirements.
2. The session behind a run, `--continue`, and the `session` command group:
   [R-SESSION-050], [R-SESSION-051], [R-SESSION-054], and [R-TUI-074], which
   moved here from M8 because resuming means seeding the engine with the
   session's own messages.

## M10: Retrieval

**Goal.** Semantic search over the workspace.

**Requirements.** All 24 `R-INDEX-*`.

**Depends on.** M1, M3 for embeddings.

**What you can do at the end.** `meow index build` indexes the repository and
`search.code` answers from it inside an agent.

**Notes.** Additive and off the critical path. Everything before it ships
without it; nothing after it depends on it. [R-INDEX-051], recording which
model built the index, is the cheap requirement that prevents silently
meaningless scores.

## M11: Providers, port, and release

**Goal.** Ship it.

**Requirements.** None new. The remaining providers satisfy the `R-LLM-*`
requirements M3 already closed, against a different vendor each.

**Depends on.** Everything.

**What to build.** OpenAI, Gemini, Copilot, OpenRouter, Voyage, and llama.
Then rewrite the shipped `.meow/` agents against the new API, which is the
acceptance test for the whole design. Then `cargo-dist`, cosign, syft, and the
release workflow, replacing GoReleaser. Then delete the Go tree and tag
`v0.3.0`.

**Notes.** The port is the milestone that finds what the specifications missed.
Budget for amendments rather than being surprised by them.

## Critical path

```text
M1 store ──┬── M2 session ──┬── M4 engine ── M5 policy ── M6 nesting ── M7 starlark ── M8 terminal
           │                │                                                              │
           └── M3 transport ┘                                              M9 continue ────┘

M10 retrieval hangs off M1 and M3 and blocks nothing.
```

M3 can run beside M1 and M2, because the provider trait needs neither. That is
the only parallelism worth taking: everything after M4 is a chain, and trying
to overlap it produces merge conflicts in the engine.

## What this plan does not decide

- **Dates.** Requirement counts are not effort, and the spike in M0 is the
  single largest source of variance.
- **The open questions in each specification.** Each carries a recommendation
  and needs a person. The three that block the earliest work are the default
  budget in `agent.md` for M4, the dead-process detection in `session.md` for
  M2, and the `synchronous` level in `store.md` for M1.
- **What happens to v0.2.1.** The Go tree stays buildable on `dev` until M11
  deletes it. Whether it gets fixes in the meantime is a call nobody has made.
